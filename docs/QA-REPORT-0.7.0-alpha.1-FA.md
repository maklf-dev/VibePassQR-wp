# گزارش QA — 0.7.0-alpha.1

## کنترل‌های اجراشده (محدود)

- پایه: بسته رسمی `event-card-manager-0.6.7-phase1.zip` ارسالی در گفت‌وگو.
- PHP lint در فایل‌های PHP: بدون خطای نحوی.
- ۵۴ آزمون مستقل شبیه‌سازی‌شده: موفق؛ فایل آزمون `workflow-smoke.php` خارج از بسته نصبی نگهداری می‌شود.
- فهرست فایل‌های تغییریافته نسبت به 0.6.7: بوت‌استرپ، Activator، Plugin Upgrade، Capabilities، Events Config، Diagnostics + چهار ماژول Workflow. فایل‌های صدور کارت، حضور، پیامک، دریافت و گزارش‌های موجود دست‌نخورده‌اند.
- عدم ساخت جدول تخریبی در سه دستور CREATE و غیرفعال‌ماندن Feature Flag بررسی شد.
- عدم اجرای Migration هنگام مراجعه به بخش عمومی سایت، AJAX و کاربران غیرمدیر به‌صورت Mock بررسی شد.
- هم‌زمانی در سطح Query و شرط `lock_version` شبیه‌سازی شد؛ آزمون هم‌زمان واقعی MySQL انجام نشده است.

## محدودیت‌ها

نتیجه موفق تست‌های Stub، **اثبات سازگاری با دیتابیس واقعی و وردپرس نیست**. تست ساخت واقعی جدول توسط `dbDelta`، قفل DDL، افزونه‌های دیگر، InnoDB، حجم واقعی داده‌ها و مسیرهای ثبت‌نام و کارت در محیط آزمایشی باید جدا انجام شود.

## تست پذیرش روی Staging (اجرای دستی)

1. Snapshot کامل دیتابیس و uploads بگیرید؛ تعداد رکوردهای `registrations`، `participants`، `ticket_tokens`، `attendance` و `sms` را ثبت کنید.
2. آلفا را **روی 0.6.7 نصب** و با مدیر کل یک صفحه معمولی وردپرس باز کنید.
3. گزارش Diagnostics را بگیرید؛ مقدار schema_version باید `1` و feature_enabled باید `false` باشد.
4. در دیتابیس تنها سه جدول Workflow و یک ستون/ایندکس افزودنی در جدول events ایجاد شده باشند. هیچ رکورد قبلی نباید تغییر کرده باشد.
5. ثبت‌نام Classic، بازیابی، کارت قبلی، PDF، QR و حضور را در Staging آزمایش کنید.
6. بارگذاری مجدد صفحه مدیریت نباید دوباره DDL اجرا کند.
7. خطاها و `ecm_db_version` را چک کنید؛ در صورت شکست Schema نباید به نسخه جدید علامت‌گذاری شود.
8. سناریوی بازگشت به نسخه قبلی را فقط روی Staging آزمایش کنید؛ جدول‌های جدید را برای بازگشت موقت پاک نکنید.

**نتیجه نهایی:** آماده بررسی آزمایشی؛ هنوز تأیید انتشار Production صادر نشده است.
